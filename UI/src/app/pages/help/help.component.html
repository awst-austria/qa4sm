Welcome to QA4SM Help

QA4SM is a free online service for validating satellite soil moisture data against ground-station observations and model references.

This help section walks you through every part of the platform — from running your first validation to interpreting, sharing, and publishing your results.

What you'll find here

Use the menu on the left to explore each topic. Here's a short overview of what each section covers:

  • Validate — how to set up and run a validation step by step: choosing datasets, applying filters, setting the reference, and configuring scaling and metrics.
  • Results — where to find your validations and open published validations from other users.
  • Dataset upload — how to upload your own datasets and use them in validations alongside the platform datasets.
  • Compare Validations — how to compare two validations side by side, or two datasets within a single validation.
  • Public API — how to run validations from the command line or your own scripts: submitting jobs, tracking progress, and downloading results using your personal API token
  • Info — help, terms of use, datasets details, and other reference material.

Validate page

How to configure and run a soil moisture validation on the Validate page?

1

Choose datasets

Select dataset name, version, and soil moisture variable.
At least two datasets are needed — one will be used as the reference.
All supported datasets are listed on the datasets page.

C3S COMBINED / v202505 / soil moisture (spatialreference)

ESA CCI SM combined / v09.2 / soil moisture (temporal reference)

2

Filter datasets

Filters narrow the data used in the validation. The available filters depend on the chosen dataset — hover over the next to each filter for an explanation.

Common filter types:

  • Variable in valid geophysical range — removes NaNs and invalid values; available for nearly every dataset.
  • Ascending / descending mode only — keeps observations from one satellite overpass direction.
  • Soil not frozen — masks values where soil temperature indicates frozen conditions (e.g. ERA5, GLDAS).
  • Threshold filters — some datasets (SMAP, SMOS, ASCAT) let you set a numeric cut-off, such as a vegetation-water-content or RFI-probability threshold.
Some datasets have mandatory filters that cannot be switched off — for example, ISMN requires a depth selection and a network selection, and SMOS L3 requires its topography and RFI filters.
3

ISMN networks & depth

When the International Soil Moisture Network (ISMN) is part of your validation, two filters must be configured.

  • Select Network(s) — choose which ISMN networks to include in the validation.
  • Select Measurement depth — choose the soil moisture measurement depth. Values are entered in metres (e.g. 0.0–0.05 for surface sensors). Only sensors within the selected range are included.
Both filters are mandatory. If no network is selected, the validation returns no result. Note also that sensors below 10 cm depth are always classified as not representative under the FRM4SM standard.
4

Add more datasets (optional)

Click Add dataset to add another product. Each dataset is configured in its own panel.

  • Minimum 2 — one dataset to validate plus one reference.
  • Up to 6 — additional datasets can be compared against the common reference (intercomparison).
  • 3 or more — unlocks Triple Collocation Analysis (see step 9).
Intercomparison: validates several satellite datasets against a common reference. Only timestamps shared by all datasets are used, so metric differences reflect actual performance — not differences in temporal coverage.
5

Set reference dataset

Choose the spatial and temporal reference. If ISMN is in the pool it is set automatically and cannot be changed.

Spatial Reference

ISMN (version)

Temporal Reference

C3S SM combined (version)

Set the temporal matching window (default 12 h, range 1–24 h).

6

Scaling

Choose how values are scaled before metric calculation and select the target dataset. When No scaling is selected no scaling reference is needed.

7

Spatial Subsetting

Define the geographical area to be validated. Enter a lat/lon bounding box or draw an area directly on the map — only locations inside this area are included in the validation. The trash icon clears all four fields. Leave the fields blank to run a global validation.

8

Temporal Subsetting

Set a validation date range in YYYY-MM-DD format. Leaving date fields empty prevents the validation from starting.

9

Metrics

Choose which metrics QA4SM calculates and how the validation is run. The defaults work for most validations — the extra options below add more detailed analysis at the cost of longer runtimes.

Validation type

Sets how the two datasets are matched up before metrics are calculated:

  • Temporal — datasets are matched temporally at each location, so that observations acquired within the same temporal matching window are compared. Metrics are computed from the resulting time series, characterising the temporal agreement between the datasets. This is the standard validation mode for soil moisture products.
  • Spatial — datasets are compared across their spatial domain rather than along the time axis. Metrics quantify the agreement between the spatial patterns of the datasets, indicating how consistently they represent the geographical distribution of soil moisture.

Additional metrics

  • Include Triple Collocation metrics — available when 3 or more datasets are selected. Triple Collocation (TC) estimates the error of each individual dataset by comparing all possible triples (the reference is always included).
  • Bootstrap TC confidence intervals — adds confidence intervals to the Triple Collocation metrics by repeating the calculation 1000 times. Warning: very slow — up to 5× the normal runtime.
  • Include Stability metrics — checks how consistent the agreement is over the full validation period, rather than giving a single overall number.
  • Include Intra-Annual metrics — breaks the results down within the year (e.g. by season or month), so you can see how performance changes across the seasons.
The bootstrapping and additional metric options noticeably increase runtime. Enable them only when you need that level of detail.
10

Anomaly calculation

Choose a method from the Method drop-down:

  • Do not calculate — use absolute values (default).
  • 35-day moving average — subtract the 35-day running mean.
  • Climatology — subtract the per-day-of-year average over a specified period.
11

Name your validation

Give the run a descriptive name to make it easier to identify in your validations list.

12

Run

Click Validate. You will receive an email with a link to the results once the run is complete — you do not need to keep the browser open.

My validations

The My validations page lists all validation runs associated with your account, ordered with the most recent first. Individual runs can be inspected, reused as the basis for a new validation, or sorted via the search and filter controls.

Pinned validations

Validations you have pinned on the Published validations page appear in a separate section at the top of the page for quick access, independent of the main list below. Each pinned entry shows its name together with action buttons to open, download, or remove it.

Searching and filtering

The header above the list shows how many validation runs were found. Three controls let you narrow the list:

  • Choose date range — show only validations run within a selected period.
  • Search by name — filter by the name you gave a validation.
  • Search by dataset — filter by a dataset used in the validation.

The validations table

Each row is one validation run. The columns are:

  • Date — when the validation was run. Click the column header to sort.
  • Name — the validation's name. Click the pencil icon to rename it.
  • Datasets — the datasets included in the run, each shown with its version, variable, and unit.
  • Spatial reference — the dataset used as the spatial reference (for example, the ISMN version).
  • Load settings — reopens the Validate page pre-filled with this run's configuration, so you can repeat or adjust it.
  • Status — the current state of the run, such as Done for a completed validation.
  • Actions — the trash icon permanently removes the validation.
Click a validation's row to open its full results page, where you can explore the charts, metrics, and downloadable files.

Opening a validation result

Click a validation's row to open its full results page. The page is divided into a summary, a result-files section with plots, and an interactive map.

Summary

The Summary box at the top reports the run itself: the start and finish time, and every dataset that was compared. For each dataset it lists the version and variable used, the filters that were applied, and whether the dataset served as the temporal or spatial reference.

Summary Statistics

The Summary statistics section reports the metrics calculated for the validation. Each metric summarises how well the datasets agree, across all locations. The following metrics are computed:

  • Pearson's r — Pearson correlation coefficient and p-value.
  • Spearman's ρ — rank correlation coefficient and p-value.
  • RMSD — root-mean-square deviation.
  • Bias — difference of means (average error).
  • ubRMSD — unbiased root-mean-square deviation.
  • MSE — mean square error, with its correlation, bias, and variance components.
  • RSS — residual sum of squares.
  • # observations — number of observations used in the comparison.
The three TC metrics are only available when Triple Collocation was enabled and three or more datasets were validated.

Result files and plots

The Validation Result files section lets you inspect and download the output. Two drop-downs control what is shown:

  • Select boxplot/map metric — choose which metric the boxplot and map display (e.g. observations, status, bias, rmse).
  • Select boxplot classification — group the boxplot by a classification, or leave it unclassified (only for ISMN).

Use Download graphs to get all plots as a ZIP (PNG and SVG), or Download NetCDF to get the result metrics file. The Bulk Plots area below shows the generated boxplots and maps for the selected metric.

Interactive map

The Click & Explore map shows the validation results geographically. Each point is a location where the metric was computed, and the colour scale at the bottom indicates its value. You can switch the displayed metric, adjust layer opacity, change the base map (e.g. Terrain), and capture or expand the view using the controls in the map corners.

Published validations

The Published validations page collects validation runs that their owners have chosen to make publicly available by publishing them to Zenodo. Each published validation has a citable DOI and is not subject to automatic removal.

The published validations page

This page works much like My validations : published runs are listed with their datasets, spatial reference, and date, and you can search and filter the list in the same way. The difference is that it shows publicly published validations from all users, not only your own.

From this list you can pin a validation. A pinned validation is kept in a separate section at the top of your My validations page for quick access, so you can easily return to results you refer to often — including published ones that are not your own.

Publishing your own validation

You can publish your result NetCDF to Zenodo under your own name to obtain a citable DOI — no Zenodo account is required.

1

Open the publish dialog

Click Publish on the validation results page. A dialog appears with pre-filled metadata.

2

Review metadata requirements

Mandatory: Title, Description, Keywords (must include qa4sm), and Name.
Optional: Affiliation and ORCID.
Changes to author details are not saved to your profile — edit those on the Profile page.

3

Publish results

Click Publish results. The upload may take a few minutes. If it fails, try again a few hours later. If the problem persists, email support with the error message.

Important: assigning a DOI means the result cannot easily be unpublished or deleted — see Zenodo's FAQ. The file is stored on Zenodo under the QA4SM project account with your name as author. If you prefer to use your own Zenodo account, download the NetCDF and upload it yourself — use qa4sm as a keyword.

Validation comparison

Available since QA4SM v2.1, the comparison module allows a logged-in user to compare existing validations — either their own or validations that have been published. It is accessed via the Compare validations button in the navigation bar.

Comparison modes

The module supports two modes. The mode is selected in the Dataset Configuration component (see step 1).

Two validations

Compares two separate validations that share the same reference dataset and one common non-reference dataset.

One validation, two datasets

Compares two non-reference datasets used within a single validation. Activated by checking Multiple non-reference datasets.

Configuring a comparison

The comparison interface consists of three components — Dataset Configuration, Validations selection, and Spatial extent — configured in order:

1

Dataset configuration

Select the dataset that was used as the reference, including its version and variable name, and choose the comparison mode. Checking Multiple non-reference datasets switches to the one validation comparison mode.

2

Validations selection

This component updates with every change of the reference dataset and lists the validations available for comparison. Add a selected validation with the Add validation button; once the maximum number has been added, the button is disabled. Added validations appear below the selection box as red Remove validation buttons, which remove the corresponding validation from the list.

3

Spatial extent

Any two validations sharing the same reference dataset can be compared. If the validations additionally share a common spatial extent, you can choose whether the comparison is performed on all points or only on the common ones. If the validations have no common points, the Include all points… option is disabled.

Comparison results

The comparison is started with the Compare button. It produces four components:

  • Comparison summary — the summaries of the chosen validations, or of the single validation when the one validation mode was used.
  • Selected comparison extent — a plot showing the area for which the comparison was performed.
  • Comparison statistics — a table of the validation statistics calculated for both validations, together with the differences between them.
  • Comparison plots — a metric-selection drop-down, plus the plots described below.
Which plots are shown depends on the spatial extent:
  • If the compared validations have no common spatial extent — or if Include all points from the selected validations was chosen — the result is a boxplot of the selected metric for each validation.
  • If the validations do share a common spatial extent, the result is a boxplot of the metric for each validation together with the difference between them, plus a map showing the differences in that metric across all compared points.

All plots and the statistics table can be downloaded individually using the buttons placed next to each object.

Note: the comparison module is still under development and runs on the fly. A comparison may fail if the validation result files are too large. If this occurs, run smaller validations — reduced via spatial subsetting — and compare those instead.

My datasets

Upload your own soil moisture datasets to validate them against the reference products available in QA4SM. Once uploaded, your dataset can be selected on the Validate page just like the built-in datasets. Your data stays private — no other user can see or access it. To get started, open the Dataset upload/My datasets page from the navigation bar.

1

Select a file

Click Select file to choose the file to upload. Only .netCDF or .zip files can be selected, and both must follow the data format guidelines. A .zip may only contain .netCDF, .csv, or .yml files — any other file type will prevent the upload. You have 5 GB of storage; contact the team if you need more.

2

Provide metadata

Once a valid file is selected, a metadata form appears. Enter a dataset name and a version name. Click Save names to confirm the metadata. This closes the form but does not start the upload.

3

Save and upload

Click Upload to begin. A blue spinner shows the upload progress. Depending on file size and connection speed, this can take from a few seconds to tens of minutes. When the transfer finishes, a message confirms the file has been uploaded and still needs to be pre-processed.

4

Review the uploaded dataset

Once uploading and pre-processing are complete, a row with the dataset's basic information appears. From this row you can edit the dataset name and version name, and select a different variable if the default one is incorrect or could not be retrieved. The Remove dataset button deletes the uploaded file — this is only possible if the dataset has not yet been used in any validation.

5

Use the dataset in a validation

Go to the Validate page and expand the dataset drop-down — your uploaded dataset is listed there. Configure the remaining validation settings and run it as usual.

Note: validations that use private data cannot be published. You can share such a validation with another user, but they cannot re-run it without access to your dataset. An uploaded dataset can only be removed while it has not been used in any validation.

Uploading your own data

QA4SM lets you upload your own soil moisture datasets and validate them against the reference products available on the platform — satellite datasets, ERA model data, and ISMN monitoring stations.

Your uploaded data is private — no other user can see, access, or download it.

Accepted file types

QA4SM accepts two upload formats:

  • NetCDF image stacks — a single .nc or .nc4 file with three dimensions: latitude, longitude, and time.
  • CSV time series — individual .csv files bundled into a single .zip archive, optionally with a metadata.yml file. Suited to irregular timestamps or specific in-situ locations.

Key requirements

  • Files must include latitude, longitude, and time information.
  • Coordinates must follow the WGS84 system (longitude −180° to 180°, latitude −90° to 90°).
  • A ZIP archive must contain only .csv files and, optionally, a metadata.yml file — no nested folders or unrelated files.
  • At least one soil moisture variable must be present.
Detailed format specifications — NetCDF structure, CSV file-naming convention, metadata, and downloadable example files — are described in the user data guidelines.

Troubleshooting

If an upload fails or your data cannot be processed, check the most common causes:

  • Invalid file type — upload a .nc/.nc4 file, or a .zip of CSV files; not other combinations.
  • Incorrect ZIP structure — remove nested folders and unrelated files.
  • Missing variables — make sure latitude, longitude, and time are all included.
  • File too large — try a smaller dataset, or contact support.
Please note: validations that use uploaded data cannot be published, due to limited traceability. Data persistence is also not yet guaranteed — future updates to QA4SM may require you to re-upload your files. For datasets larger than several GB, contact support@qa4sm.eu before uploading.

Public API

The QA4SM Public API lets you work with the service from the command line or your own scripts. You can submit validation jobs, track their progress, and download results as soon as they are ready. Access is secured with your personal API token.

You can request a personal API token from your User Profile page. The token identifies your account — keep it private and do not share it.

Authentication

Every request must include your personal token in the Authorization header, in the form Authorization: Token <YOUR_USER_TOKEN>. Requests without a valid token are rejected.

Submit a validation

Start a new validation by sending a POST request. <CONFIG_JSON_FILE> is a JSON file that defines the datasets, filters, time ranges, and metrics for the validation job. 

$ curl -X POST \
          -H "Authorization: Token <YOUR_USER_TOKEN>" \
          -H "Content-Type: application/json" \
          -d @<CONFIG_JSON_FILE> \
        https://qa4sm.eu/api/start-validation-with-token

List your validation runs

Retrieve your validation runs with a GET request. The example below formats the response as a readable table showing each run's id, name, datasets, and progress. 

$ curl -X GET \
          -H "Authorization: Token <YOUR_USER_TOKEN>" \
          https://qa4sm.eu/api/my-validation-runs-with-token | jq -r '
          .validation_runs[] |
          [.id, .name, (.datasets | join("; ")), .progress] |
          @tsv
        ' | column -t

Download results

Once a validation has finished, download its result files as a ZIP archive. Replace <VALIDATION_RUN_ID> with the id of the run (as returned by the previous request) and <OUTPUT_FILE> with the name to save it under. 

$ curl -X GET \
          -H "Authorization: Token <YOUR_USER_TOKEN>" \
          "https://qa4sm.eu/api/download-result-file-with-token/<VALIDATION_RUN_ID>/zip" \
        --output <OUTPUT_FILE>.zip
A typical workflow uses all three endpoints in sequence: submit a validation, poll the run list until its progress reaches completion, then download the result ZIP using the run id.
